# v3.0 备份/恢复修复清单

## 你反馈的问题与真因

| 现象 | 真因 | 修复 |
|---|---|---|
| 角色卡标签没恢复 | 恢复顺序是「标签」先于「角色」，`role_tags` 有外键指向 `roles`，被 SQLite 直接拒绝 | ① 恢复前 `PRAGMA foreign_keys=OFF`，写完再打开 ② 顺序改成 roles → world_books → role_tags → sessions → messages |
| 聊天没恢复 | `chat_messages` 依赖 `chat_sessions`，批量插入时失败被静默吞掉 | 同上，按依赖顺序 + 外键关闭 + 每条结果计数，失败会明确报出来 |
| API 没恢复 | 恢复函数里根本没有 `api` 分支（只处理了 cards/chat/settings/vip） | 新增 `api` 分支：写回 `S.models / curId / customOn / aiId` 再 `saveState()` |
| 备份像是空的 | 每个段单独调用 `bkFlush()`，20 个对话就整файл重写 20 次；中途失败只留下不完整文件 | 改成批量模式：段先攒着，最后 `bkFlush()` 一次 |
| 版本号加载失败 | `version.json` 末尾多了逗号（JSON 不合法），`JSON.parse` 直接抛错 | 重写文件，去掉多余逗号和说明字段 |

## 关键改动

### 1) 恢复顺序与外键
```
PRAGMA foreign_keys=OFF
  → roles / world_books
  → role_tags
  → chat_sessions
  → chat_messages
  → 媒体文件写回（Filesystem.writeFile recursive）
  → settings（localStorage）
  → api（S 状态 + saveState）
  → vip（仅真卡密）
PRAGMA foreign_keys=ON
```

### 2) 批量插入
每 80 行拼一条多值 `INSERT OR REPLACE`，几千条消息也只有几十次 db 调用。

### 3) 有结果、有反馈
恢复完成 toast：
```
恢复完成：12 卡 / 34 标签 / 8 对话 / 1560 消息 / 21 文件
```
备份完成 toast 同样给数量。

### 4) 数据库自检
设置卡里新增一行：
```
数据库 piupiu：12 个角色 / 8 个对话 / 1560 条消息
```
→ 如果这里显示 0，说明 SQLite 通道没连上（不是备份逻辑的问题），一眼能区分。

### 5) 连接掉线自愈
查询失败时自动 `open({database:'piupiu'})` 再重试一次。

### 6) 体积保护
- 单文件 12 MB 上限（base64 后约 16.8 MB）
- 整包 > 160 MB 时跳过写入并提示，避免 OOM
