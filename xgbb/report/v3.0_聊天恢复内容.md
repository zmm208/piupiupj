# v3.0 聊天恢复后内容为空

## 定位过程
`ChatView` 读取消息的真实 SQL：

```sql
SELECT message_index, message_id, role, content,
       json_extract(message_json,'$.speakerName') AS name,
       json_extract(message_json,'$.swipe_id')   AS swipe,
       json_type(message_json,'$.image')         AS image
FROM chat_messages
WHERE session_id = ? AND message_index >= ? AND role IN ('user','assistant')
ORDER BY message_index
```

所以只要 `chat_messages` 里没有行，或者 `role` 不是 user/assistant，会话打开就是空白 —— 即使
`chat_sessions` 恢复成功（列表里能看到标题、能点进去）。

## 三个修复

### 1) 用 session_json 兜底生成消息
会话的 `session_json` 里通常也存着完整的 `messages` 数组。备份/恢复时会检查：
如果 `chat_messages` 里没有该会话的行，就从 `session_json.messages` 反推并补写：

```js
{ session_id, message_index, message_id, role, content, timestamp, message_json }
```

role 归一化为 `user / assistant / system`，避免被 ChatView 的 `WHERE role IN (...)` 过滤掉。

- 备份时补齐：`mine = bkMessagesFromSession(s, mine)`
- 恢复时补齐：会话没有消息就现场生成

### 2) 原生写入失败自动回退
原生 `dbExec` 在 App 正占用数据库时可能失败（返回 false）。
现在失败会自动走插件路径（逐表 INSERT OR REPLACE），两条路都试完才报失败。

### 3) 恢复后做写入校验
恢复完成会重新 dump 一次数据库，提示真实结果：

```
恢复完成：6 卡 / 5 对话 / 218 消息 → 库里现有 5 对话 / 218 消息
```

- 如果后面的数字是 0，说明写库没成功（被占用/权限）
- 如果对话有、消息 0，说明备份里就没有消息，会走 session_json 兜底

## 测试步骤
1. 打开备份开关 → 立即备份（记下提示里的对话数、消息数）
2. 查看备份内容 → 聊天条目里应显示「N 条消息」
3. 删掉一个对话 → 恢复备份，勾选它 → 恢复
4. 看提示：`... → 库里现有 X 对话 / Y 消息`
5. 进回忆页点开该对话

如果第 4 步消息数是 0，把整句提示发我——能直接区分是"备份里没消息"还是"写库失败"。
